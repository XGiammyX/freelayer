# Device Passport Package-Boundary Audit (TECH-ID-08)

- **Date:** 2026-07-26
- **Branch:** `tech/identity-device-passport-v1` (stacked on `tech/identity-device-key-model-v1` / TECH-ID-07, PR #62)
- **Module:** `@freelayer/identity` → [`packages/identity/src/device-passports/`](../../packages/identity/src/device-passports) (16 files)

This audit covers the package/dependency boundary of the **Device Passport** module and proves it stays within its declared limits: a **versioned, LOCAL, NON-cryptographic root-to-device authorization contract** — a bounded candidate link request, an attenuated unsigned passport claim, a local policy-only approval, restriction, and local revocation — **not** a signature, **not** a signed or verified passport, **not** attestation, **not** DevicePosture, **not** proof-of-safety, **not** real-world identity, **not** a hardware identifier, and **not** a `RoomMemberRef`. A `DevicePassportV1` references **exactly one** identity root (`issuerRootId`) at **exactly one** authority epoch (`issuerAuthorityEpoch`), lives in a **separate** aggregate (`DevicePassportStateV1`), holds **no** key material and **no** signature (`signatureState: "not_implemented_gate_f"`, `operationalAuthority: "none"`), and never mutates a root, persona, room binding, RoomOS membership, or the authoritative TECH-ID-07 `DeviceAuthorizationRecordV1`. A local unsigned approval grants **no** operational device authority. There is no network, no persistence beyond memory/null, no cryptography, no QR/transport, no remote activation/revocation, and no hardware/posture binding. Companion notes: [TECH_ID_08_PRECHECK.md](TECH_ID_08_PRECHECK.md), threat model [TECH_ID_08_DEVICE_PASSPORT_THREAT_MODEL.md](TECH_ID_08_DEVICE_PASSPORT_THREAT_MODEL.md), implementation research [DEVICE_PASSPORT_IMPLEMENTATION_RESEARCH.md](../research/DEVICE_PASSPORT_IMPLEMENTATION_RESEARCH.md), main audit [TECH_ID_08_DEVICE_PASSPORT_AUDIT.md](TECH_ID_08_DEVICE_PASSPORT_AUDIT.md). House style follows [DEVICE_KEY_MODEL_BOUNDARY_AUDIT.md](DEVICE_KEY_MODEL_BOUNDARY_AUDIT.md) (TECH-ID-07).

The device-passports module depends **only** on `@freelayer/privacy` (`PolicyDecision`/`isPolicyDecision`, `PolicySideEffectScope`, `PrivacyMode`), sibling identity identifiers/types (`../identifiers`, `../identity-types`), the injected-clock helpers (`../ephemeral`), the reused TECH-ID-07 device surface (`../devices`), and, transitively via `../identifiers`, `@freelayer/security` (`Brand`). It imports **no** UI, **no** camera/QR, **no** network transports, **no** Crypto implementation, **no** Secure Device / DevicePosture / ScreenShield / attestation implementation, **no** platform / OS / hardware APIs, **no** history/message storage, and — critically — **it never imports `@freelayer/rooms`** and never touches a RoomOS mutation API. (Verified: the module's only cross-package imports are `@freelayer/privacy`, `../identifiers`, `../identity-types`, `../ephemeral`, and `../devices`.)

Like the TECH-ID-07 device model, the passport module needs **no** RoomOS read-model mirror: a room is referenced only as an opaque `RoomIdentityBindingId` brand inside a reused `DeviceAuthorizationScopeV1` (a *maximum future context*, never a membership, role, or graph read). It reads no RoomOS-owned state and asserts no cross-package atomicity with membership. The one authority it consumes beyond the TECH-ID-07 surface is the new **local authority epoch** (`IdentityAuthorityEpoch`, [`identifiers.ts`](../../packages/identity/src/identifiers.ts)) — a positive local counter changed only by explicit root lifecycle operations, never time, never a key version, never caller-controlled — supplied caller-resolved through `DevicePassportRootRefV1` / `DevicePassportApproverContextV1`, not stored on the root record.

## Separate aggregate / repository — isolation rationale

Passports and link requests are held in a **separate** `DevicePassportStateV1` (`persistenceClass: "current_process_memory" | "null"`; carries a `processEpoch`, a `requests[]` list, and a `passports[]` list — [`passport-types.ts`](../../packages/identity/src/device-passports/passport-types.ts)), served by a **separate** `DevicePassportRepositoryV1` (`InMemory…` = current-process memory, or `Null…` — [`passport-repository.ts`](../../packages/identity/src/device-passports/passport-repository.ts)), keyed to a **caller-resolved** `DevicePassportRootRefV1` + `DevicePassportApproverContextV1`. Records are never added to a `LocalIdentityRootV1`, an `EphemeralIdentityRootV1`, a `RoomIdentityBindingV1`, a `RoomMembershipRecordV1`, or a TECH-ID-07 `DeviceAuthorizationRecordV1`. Deliberate isolation, not incidental layering:

- **Revocation cannot disturb the root, persona, binding, membership, or device record.** Because the aggregate references the root by id/epoch (`DevicePassportRootRefV1`) and lives in its own store, prepare/approve/restrict/expire/revoke rewrite only passport (and their originating request) records ([`passport-reducer.ts`](../../packages/identity/src/device-passports/passport-reducer.ts)); the root lifecycle, key-material state, persona label, room binding, RoomOS membership, and the authoritative device authorization are untouched. `LocalDevicePassportRevocationResultV1` discloses exactly what a revoke does **not** do (`remoteDeviceAffected: false`, `deviceAuthorizationAffected: false`, `messageKeysRotated: false`, `roomKeysRotated: false`, `deviceDataErased: false`, `cryptographicRevocationPerformed: false`).
- **The device authorization record stays authoritative; a passport is never a second source of truth.** A passport claim carries `operationalAuthority: "none"`, `signatureState: "not_implemented_gate_f"`, `verificationState: "not_verified_no_crypto"`; `devicePassportGrantsOperationalAuthorityV1` returns `false` unconditionally. The caller supplies the root's usability/eligibility (`rootActive` / `rootApprovalEligible`) and the approver's maximum scope/capabilities rather than the module reaching into root or device internals.
- **Fail-closed blast radius.** A bug in one path cannot leak a passport into the identity vault, the binding, the membership graph, or the device store, or vice versa; the repository accepts only its own aggregate type and only a decision whose `sideEffect` begins with `identity.device_link_request.` or `identity.device_passport.` (`isAuthentic` — [`passport-repository.ts`](../../packages/identity/src/device-passports/passport-repository.ts)).
- **Structural uniqueness, approved-once, terminal tombstones.** The reducer holds at most `maximumPendingRequestsPerRoot: 3` pending requests per root, refuses a duplicate request/challenge id, admits **one draft per originating request** (`draft_already_exists`), and guards double-approval (`DeviceLinkRequestAlreadyApprovedError`); every tombstone (`rejected` / `expired` / `revoked`) is terminal via [`passport-lifecycle.ts`](../../packages/identity/src/device-passports/passport-lifecycle.ts). The signed issuer states are structurally unreachable (below).

## What a consumer may consume (narrow, safe)

Only policy-safe result surfaces, mapped by the (future) facade — never the internal aggregate:

- **A caller / UI (local)** may consume only a **redacted `DevicePassportSummaryV1`** — trust flags `cryptographicallyIssued` / `cryptographicallyVerified` / `operationalAuthority` / `remotelyAccepted` / `hardwareAttested` / `postureVerified` fixed `false`; it reports the exact `lifecycle` + `authenticity` (never "trusted/valid/verified" generically) and, only when policy allows, a coarse `scopeKind` / `capabilityCount` / `keyPurposeCount` / `expiresAtLocal`; strict modes set `redacted: true` and omit them — built only behind its own `identity.device_passport.summary.read` decision (`assertDevicePassportSummaryDecisionV1` — [`passport-summary.ts`](../../packages/identity/src/device-passports/passport-summary.ts)). The caller never receives the raw claims, the scope internals, the key-slot commitments, the root/authorization ids, the challenge/request ids, or the authority epoch. Audit events are `redacted: true` (category + outcome + mode + reason code only).
- **Crypto (later, after Gate F)** may consume the **empty, purpose-separated key-slot commitments** a passport declares (`DevicePassportKeySlotCommitmentV1`: `candidatePublicMaterial: "not_present_gate_f"`, `algorithm: "not_selected_gate_f"`, `commitmentBinding: "not_implemented_gate_f"` — [`passport-claims.ts`](../../packages/identity/src/device-passports/passport-claims.ts)). No commitment holds key bytes today; when Gate F ships, the signature binds material to a slot's fixed, one-per-purpose commitment, never treating a commitment as a present key and never reading a slot id as authority.

Both are architecture-rule contracts: no facade is wired yet (Gate G). The result types exist and are redaction-correct; the passport↔UI and Crypto↔commitment integrations are later tasks.

## What must NEVER cross the boundary (never-cross list)

- **A signature / verification / issuance / acceptance** — a passport is never signed, verified, issued, or remotely accepted here: `signatureState: "not_implemented_gate_f"`, `verificationState: "not_verified_no_crypto"`, `cryptographicallyIssued: false`, `cryptographicallyVerified: false`, `remotelyAccepted: false`. The `issued_future_signed` / `accepted_future_verified` lifecycles are declared for the contract but are **not constructible in production** — `assertDevicePassportTransitionV1` throws `future_signed_state_forbidden_in_production` for either target ([`passport-lifecycle.ts`](../../packages/identity/src/device-passports/passport-lifecycle.ts)); the guardrail bans the literals (below);
- **Operational device authority** — an approval is policy-only (`approvalState: "approved_local_policy_only"`, `operationalAuthority: "none"`); `devicePassportGrantsOperationalAuthorityV1` is a hard `false`; there is no command to sign / issue / verify / remotely-accept / transport / activate a passport (`DEVICE_PASSPORT_FUTURE_GATED_COMMAND_NAMES` reject as `DevicePassportIssuanceUnavailableError`);
- **key material / crypto** — `signature` / `signed` / `publicKey` / `privateKey` / `rootSecret` / `recoveryKey` / `historyKey` are rejected caller fields (`FORBIDDEN_FIELDS`, [`passport-validation.ts`](../../packages/identity/src/device-passports/passport-validation.ts)); the module uses no `crypto`/`webcrypto`/`generateKeyPair`/`createSign`/`randomBytes` (guardrail `PASSPORT_CRYPTO_RE`); key-slot commitments hold no material;
- **hardware / device / OS metadata** — no serial, model, MAC, IMEI, hostname, OS build, or attestation; `hardwareId` / `serialNumber` / `imei` / `hostname` / `osBuild` are rejected caller fields, `attestation` / `devicePosture` / `screenShieldActive` / `managedBunker` raise `DevicePassportAttestationConfusionError`. A candidate/subject ref (`LocalDeviceRef`, `dev-…`) is an opaque local handle, never a hardware identifier; passport/request/challenge ids (`pass-…` / `lreq-…` / `lchal-…`) encode no hardware, key, root/room/relationship, timestamp, posture, or authority data;
- **DevicePosture / attestation as authority** — a passport carries no posture/attestation claim (`devicePostureClaimIncluded: false`, `attestationClaimIncluded: false`); posture may only **tighten** (`postureAtRisk` / `policyStricter` deny in the stale-context checks — [`passport-validity.ts`](../../packages/identity/src/device-passports/passport-validity.ts)); the guardrail bans `postureAuthorizesPassport` / `attestationAuthorizesPassport`;
- **RoomOS role / membership as authority** — no room role or membership approves a passport; identity never imports `@freelayer/rooms`; the guardrail bans `roomRoleApprovesPassport` / `membershipApprovesPassport`. A passport neither grants nor proves membership;
- **root internals** — the private root id / key-material state / persona label; a passport claim exposes only opaque brands and never serializes root material; the caller asserts root usability/eligibility via `DevicePassportRootRefV1` rather than the module reading the root aggregate;
- **scope / capability widening, wildcard, delegation, recovery** — grants are attenuation-only against **both** the request and the approver (`resolveDevicePassportGrantV1` reuses `attenuateDeviceAuthorizationScopeV1`; capabilities are the requested ∩ approver intersection; `DEVICE_UNAVAILABLE_CAPABILITIES` = `identity.device.add_future` + `identity.recovery.approve_future` reject); `delegationAllowed` / `recoveryAuthorityGranted` are fixed `false` on claims and rejected as caller fields; the guardrail bans `widenPassportScope` / `wildcardCapability`;
- **root-secret / history / QR transport** — `rootSecretTransferAllowed: false`, `historyTransferIncluded: false`; `transport: "not_implemented_gate_e"`, `qrRepresentation: "not_implemented_gate_e"`; the guardrail bans `transferRootSecret` / `transferHistory` / `encodePassportQr` / `scanPassportQr` / `serializePassportWire` and camera/QR APIs (`PASSPORT_QR_RE`);
- **a persistent registry / correlation surface** — no disk/localStorage/sessionStorage/indexedDB, no exported passport list or history (guardrail bans `persistPassportRegistry` / `persistPassportHistory` + storage tokens; policy `identity.device_passport.persistence` is `deny`); summaries carry no cross-root linkage;
- **remote effects** — no `fetch`/`WebSocket`/`RTCPeerConnection` (guardrail `PASSPORT_NETWORK_RE`); revocation is local-only and claims no remote deletion, session/key rotation, or erasure (guardrail bans `remotePassportRevoke` / `globalPassportRevocation` / `cryptographicRevocationPerformed: true`).

## No peer-facing text, no side effects, no automatic mutation

The device-passports module performs no storage/network/notification/AI/crypto/randomness. A link request carries no free text at all (no label, no title); it names a candidate only by opaque ref. Creating, submitting, rejecting, expiring, revoking a request, or preparing/approving/restricting/expiring/revoking a passport does not create, alter, or revoke a root, persona, room binding, RoomOS membership, or device authorization, and produces no remote effect. There is no directory, no QR flow, no import, no signing, and no attestation — those commands are future-gated and simply do not exist (`DEVICE_PASSPORT_FUTURE_GATED_COMMAND_NAMES` reject as unavailable — [`passport-commands.ts`](../../packages/identity/src/device-passports/passport-commands.ts)). A request or passport is never seeded automatically from a hardware signal, a posture reading, a room role, or a `RoomMemberRef` — it comes only from an explicit, discriminated, exact-shape command with injected ids and clock.

## Note on the existing Secure Device / posture guards + the new passport guard

The passport policy makes an **honest negative disclosure** — `devicePostureClaimAllowed: false`, `attestationClaimAllowed: false`, `cryptographicIssuanceAvailable: false`, `remoteAcceptanceAvailable: false`, `qrTransportAvailable: false` in every privacy mode ([`passport-policy.ts`](../../packages/identity/src/device-passports/passport-policy.ts)). A **new** static guardrail, `check:no-device-passport-bypass` ([`scripts/check-no-device-passport-bypass.mjs`](../../scripts/check-no-device-passport-bypass.mjs)), extends the device token-guard family with passport-specific overclaims (signed/verified/issued/accepted passport, operational-authority grants, second-device activation, root-secret/history transfer, QR/wire serialization, posture/attestation/room-role approval, scope widening / wildcard / delegation / recovery, persistent registry, remote/global revocation, generic patch, direct storage) plus passport-module-only regexes banning crypto, camera/QR, raw claim logging, and network calls. It allowlists the files that legitimately name rejected fields or declare the future-signed literals as data (`passport-validation.ts`, `passport-types.ts`, `passport-lifecycle.ts`, `passport-commands.ts`, and `packages/privacy/src/policyMatrix.ts`), confirming the boundary from the other side: the passport model discloses the **absence** of signatures/verification/attestation/posture authority rather than implementing or consuming them, and Secure Device stays externalized.

## Honest enforcement status

- **Enforced today:** dependency set (privacy + security + sibling identity identifiers/types + injected-clock helpers + the reused TECH-ID-07 device surface only), no `@freelayer/rooms` import, no UI/camera/QR/transport/crypto/Secure-Device/platform/history-storage imports, memory/null-only storage, separate aggregate with root-by-`DevicePassportRootRefV1` (no root/persona/binding/membership/device rewrite), exactly one root + one authority epoch per passport, attenuation-only scope + capability intersection against both request and approver, no producible signed/verified/issued/accepted state (`assertDevicePassportTransitionV1` throws), no producible operational-authority state (`devicePassportGrantsOperationalAuthorityV1` → `false`), fail-closed stale-context re-checks (`assertDeviceLinkRequestCurrentV1` / `assertDevicePassportDraftCurrentV1`) on process restart / root-not-usable / root/epoch/revision/candidate drift / passed deadline / posture-or-policy tightening, exact-scope `identity.device_link_request.*` / `identity.device_passport.*` `PolicyDecision` on every pipeline and repository op (re-checked by `isAuthentic`, which requires the passport-namespace prefix), the +18 Policy Matrix rows (incl. 7 structural future-gates/denies), and the `check:no-device-passport-bypass` static guardrail (wired into `audit:privacy` and CI, with a `tests/fixtures/device-passport-bypass/` intentional-failure fixture).
- **Architecture-rule (not yet code-enforced end to end):** no sdk/core Identity Firewall facade maps a redacted `DevicePassportSummaryV1` or the key-slot commitments to a UI or (future) Crypto consumer — **no facade is wired** (Gate G). The narrow result surfaces exist and are redaction-correct, but "what a consumer may consume" describes the intended contract, not a live integration.
- **Future-gate:** the signed root↔device passport signature, verification, and remote acceptance are **Gate F**; the QR / link wire format + Capsule transport are **Gate E**; synchronization / distributed / remote passport revocation are **Gate H**. This module claims none of them, and no external Secure Device / Endpoint Defense capability is implemented in core — only contracts, policy inputs, and honest disclosures.

## Mandatory honest boundary statements

A Device Passport is **not** DevicePosture; a passport is **not** hardware attestation; a passport is **not** proof-of-safety; a passport is **not** proof of real-world identity. A device is **not** a person; a passport id is **not** a hardware identifier; a local unsigned approval is **not** cryptographic authorization; a QR code is only a transport representation, never authorization; room membership does **not** authorize a device; DevicePosture may **restrict** use of a device but can **neither issue nor validate** a passport. There is **no cryptographic passport**, **no replay-resistant linking**, **no remote activation/acceptance**, **no remote/cryptographic revocation**, **no attestation**, and **no hardware/posture/endpoint guarantee** in this module; it is **not safe for real secrets**. Deferred: Gate F (signing / verification / signature format), Gate E (QR / link wire format / Capsule transport), Gate H (synchronization / distributed revocation). Secure Device / Endpoint Defense / ScreenShield remain **externalized**, never implemented or consumed in core.

## Unresolved dependency direction (honest)

As in TECH-ID-03/04/05/06/07, no shared-contract package was introduced for cross-domain references; the identity-local brands (root ids, authority epoch, device scopes/capabilities, key purposes, opaque device/passport refs) suffice, and — unlike the room-alias module — the passport model needs no RoomOS read-model mirror because it reads no RoomOS-owned state. Its honest concessions are that the **caller**, not the module, (a) resolves the root's usability and approval-eligibility into `DevicePassportRootRefV1`, (b) resolves the approver's maximum scope + capabilities and the current authority epoch into `DevicePassportApproverContextV1` (`cryptographicRootControlProven: false`), and (c) supplies the local clock + process epoch; the module fails closed on any drift but cannot itself prove the root is current or that the epoch is authentic (that is a caller / Gate F obligation). If a future task needs bidirectional root↔device↔passport↔RoomOS types, extract a `@freelayer/contracts` package and move the ref brands there. The passport↔UI and Crypto↔commitment integrations remain later tasks (Gate G / Gate F); this audit fixes the boundary they must honor when they land — above all, that a passport is local, non-cryptographic metadata, that identity never imports or mutates RoomOS or the device record, and that neither a passport, a posture reading, a room role, nor an unsigned approval is identity, authority, verification, a signature, or a key.

## Verdict

**Complete (boundary).** The Device Passport module holds a clean, cycle-free dependency graph: privacy + security + sibling identity identifiers/types + injected-clock helpers + the reused TECH-ID-07 device surface only, with **no** `@freelayer/rooms`, UI, camera/QR, transport, crypto, Secure Device, platform, or history-storage import; a separate memory/null aggregate keyed to a caller-resolved root ref + approver context that never rewrites a root, persona, binding, membership, or device record; attenuation-only grants against both request and approver; no producible signed/verified/issued/accepted or operational-authority state; fail-closed stale-context re-checks; exact-scope `identity.device_link_request.*` / `identity.device_passport.*` gating at the pipeline and again at the repository; +18 Policy Matrix rows (7 structural future-gates/denies); and a dedicated static guardrail wired into `audit:privacy` and CI. The passport↔UI and Crypto↔commitment consumer contracts are documented and structurally supported but not yet wired (Gate G). No boundary regression found.
