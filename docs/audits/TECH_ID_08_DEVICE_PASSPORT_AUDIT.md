## Source research

## The deliverable (two record classes in a separate aggregate)

TECH-ID-08 introduces exactly two authoritative local record classes in a **separate** aggregate `DevicePassportStateV1` (`persistenceClass: "current_process_memory" | "null"`; carries a `processEpoch`, a `requests[]` list, and a `passports[]` list — [`passport-types.ts`](../../packages/identity/src/device-passports/passport-types.ts)), keyed to a caller-resolved `DevicePassportRootRefV1` + `DevicePassportApproverContextV1`. Neither is a key, a signature, a verified credential, identity, DevicePosture, attestation, a `RoomMemberRef`, or a hardware identifier.

1. **`DeviceLinkRequestV1`** — a bounded, non-authoritative candidate request for FUTURE authorization ([`passport-link-requests.ts`](../../packages/identity/src/device-passports/passport-link-requests.ts)). It names a candidate only by opaque `LocalDeviceRef`, carries the requested scope / capabilities / key-slot commitments, binds one `rootId` + `rootAuthorityEpoch`, and holds no hardware id, phone/email/account, root secret, device private key, DevicePosture, attestation, label, history material, or network endpoint. `transport` / `qrRepresentation` are `"not_implemented_gate_e"`; `candidateBinding` is `"local_placeholder_unverified"`; `persistence: "forbidden"`.
2. **`DevicePassportV1`** — a local, unsigned authorization claim a Gate-F signature would LATER authorize ([`passport-types.ts`](../../packages/identity/src/device-passports/passport-types.ts)). It fixes `signatureState: "not_implemented_gate_f"`, `verificationState: "not_verified_no_crypto"`, `operationalAuthority: "none"`, `remotelyAccepted: false`, `cryptographicallyIssued: false`, `cryptographicallyVerified: false`, `persistence: "forbidden"`, and an `approvalState` of `"not_reviewed" | "approved_local_policy_only" | "rejected"`.

## Identifiers (opaque, local, non-hardware)

Passport references are opaque local ids ([`passport-identifiers.ts`](../../packages/identity/src/device-passports/passport-identifiers.ts)): `DevicePassportId` (`pass-…`), `DeviceLinkRequestId` (`lreq-…`), `DeviceLinkChallengeId` (`lchal-…`), each `^[a-z0-9][a-z0-9_-]{2,127}$`, length 4–128, no `@`. They encode **no** hardware/OS data, no root/persona/room/relationship data, no timestamp-as-authority, no public key/fingerprint, no posture, and no authority; a `DeviceLinkChallengeId` is an opaque correlation-resistant handle **only** — until Gate F it is **not** a cryptographic nonce and provides **no** replay-proof guarantee. Ids are **injected** into the reducer (`DevicePassportGeneratedIdsV1`), never minted with randomness inside it.

## Link requests (bounded, injected-clock lifetime, current-process only)

A `DeviceLinkRequestV1` moves through an explicit lifecycle `draft_candidate_local → pending_local_review → approved_local_unsigned → {rejected_tombstone | expired_tombstone | revoked_tombstone}` (tombstones terminal), enforced by `assertDeviceLinkRequestTransitionV1` ([`passport-lifecycle.ts`](../../packages/identity/src/device-passports/passport-lifecycle.ts)); `consumed_future` is declared for the contract but **unreachable** (an empty transition set). Its validity is an **engineering** lifetime, not cryptographic freshness: `DeviceLinkRequestValidityV1` fixes `currentProcessOnly: true`, `crossRestartValidity: false`, `cryptographicFreshnessAvailable: false`, `oneTimeCryptographicEnforcementAvailable: false`, with `DEVICE_LINK_REQUEST_LIMITS_V1` bounding lifetime to `[60_000, 900_000]` ms (default `300_000`) and pending requests to `maximumPendingRequestsPerRoot: 3`. The reducer rejects an out-of-band lifetime (`bad_lifetime`), a 4th pending request per root (`pending_limit`), a duplicate request/challenge id (`duplicate_id`), and an unparseable clock (`bad_clock`). Deadline expiry is evaluated by `isDeadlinePassedV1`, which fails **closed** on a backward or unparseable clock ([`passport-validity.ts`](../../packages/identity/src/device-passports/passport-validity.ts)).

## Claims + validity + key-slot commitments (exact, no material)

`DevicePassportClaimsV1` ([`passport-claims.ts`](../../packages/identity/src/device-passports/passport-claims.ts)) are the **exact** commitments a future Gate-F signature would authorize: `issuerRootId` + `issuerAuthorityEpoch`, `subjectDeviceRef` + `subjectAuthorizationId`, `grantedScope` + `grantedCapabilities`, `keySlotCommitments`, `originatingRequestId` + `originatingChallengeId`, `issuanceRevision`, and a `validity`. Every delegation/recovery/exfiltration flag is fixed **false** — `delegationAllowed`, `recoveryAuthorityGranted`, `rootSecretTransferAllowed`, `historyTransferIncluded`, `devicePostureClaimIncluded`, `attestationClaimIncluded`. A `DevicePassportKeySlotCommitmentV1` holds **no** key material: `candidatePublicMaterial: "not_present_gate_f"`, `algorithm: "not_selected_gate_f"`, `commitmentBinding: "not_implemented_gate_f"` — one commitment per requested purpose, reusing the TECH-ID-07 `DeviceKeyPurposeV1` / `DeviceKeySlotId`. `DevicePassportValidityV1` binds the `rootAuthorityEpoch` + a `minimumDeviceAuthorizationRevision` and honestly disclaims `trustedTimeAvailable: false`, `cryptographicFreshnessAvailable: false`, `crossRestartDraftValidity: false`. The claims carry no alias/contact/room/relationship graph, no history data, no wildcard capability, and no recursive delegation.

## Passport record + lifecycle (draft → approved_unsigned → restricted; no signed state)

A `DevicePassportV1` moves through `draft_local → approved_local_unsigned → restricted_local → {expired_tombstone | revoked_tombstone}` (tombstones terminal), enforced by `assertDevicePassportTransitionV1` ([`passport-lifecycle.ts`](../../packages/identity/src/device-passports/passport-lifecycle.ts)); `restricted_local → restricted_local` narrows further. The signed issuer states `issued_future_signed` / `accepted_future_verified` are declared in the union and `DEVICE_PASSPORT_FORBIDDEN_PRODUCTION_LIFECYCLES` but are **not constructible in production**: the transition function throws `future_signed_state_forbidden_in_production` for either target **before** consulting the transition table, and both have empty outbound sets. An approval sets `approvalState: "approved_local_policy_only"` and never advances `operationalAuthority` past `"none"`. The hard boundary is codified: `devicePassportGrantsOperationalAuthorityV1` ([`passport-reducer.ts`](../../packages/identity/src/device-passports/passport-reducer.ts)) returns `false` unconditionally.

## Grant attenuation (against both request AND approver; no widening)

`resolveDevicePassportGrantV1` ([`passport-attenuation.ts`](../../packages/identity/src/device-passports/passport-attenuation.ts)) derives a passport's grant by **attenuation only**. The scope is computed by reusing the TECH-ID-07 `attenuateDeviceAuthorizationScopeV1({ current: approver.maximumScope, requested: request.requestedScope })` — equal-or-narrower under the **same root** only; any widening, cross-root, incomparable, or read-only→writable transition throws `DevicePassportScopeEscalationError`. Capabilities are the **intersection** of the request and the approver's maximum (attenuation-only, deduplicated); the structurally unavailable `DEVICE_UNAVAILABLE_CAPABILITIES` (`identity.device.add_future` + `identity.recovery.approve_future`) are rejected outright as `DevicePassportCapabilityEscalationError` (`forbidden_capability`). There is no wildcard, no recursive delegation, and the grant never silently broadens for usability. Restriction (`restrict_local`) re-applies the same attenuation against the passport's own current grant.

## Authority-epoch binding (root recovery invalidates stale drafts)

A passport binds one `IdentityAuthorityEpoch` ([`identifiers.ts`](../../packages/identity/src/identifiers.ts)) — a **positive local counter** that changes ONLY through explicit root lifecycle operations (recovery / rotation / compromise response), is **not** time, **not** a key version, **not** globally synchronized, and never caller-controlled (`FIRST_IDENTITY_AUTHORITY_EPOCH = 1`; `nextIdentityAuthorityEpoch` increments; `validateIdentityAuthorityEpoch` bounds it). `IdentityAuthorityEpochStateV1` ([`identity-types.ts`](../../packages/identity/src/identity-types.ts)) records the change reason — `initial_local | recovery_future | root_rotation_future | compromise_response | administrative_reset_forbidden` — encoding that there is **no** administrative reset. A root recovery/rotation increments the epoch, so a passport claim or link request bound to a superseded epoch fails closed (`DevicePassportRootEpochMismatchError`) at both the reducer and the stale-context re-checks. This is a **local** re-verification fence, not a signed generation or distributed revocation.

## Stale-context invalidation (fail-closed re-checks)

Two re-check helpers fail **closed** on any drift, mirroring the TECH-ID-07 snapshot discipline ([`passport-validity.ts`](../../packages/identity/src/device-passports/passport-validity.ts)):

- `assertDeviceLinkRequestCurrentV1` — denies on process restart (`currentProcessEpoch !== storedProcessEpoch`), a not-usable root (`!rootActive`), root/epoch/revision/candidate drift, a non-operational request lifecycle, a passed deadline, and DevicePosture/policy tightening (`postureAtRisk === true || policyStricter === true`).
- `assertDevicePassportDraftCurrentV1` — denies on process restart, a not-eligible root (`!rootApprovalEligible`), root/epoch/revision/candidate drift, a non-operational passport lifecycle, a passed deadline, and posture/policy tightening.

Stale authorization is **never** silently refreshed. These are engineering checks over an injected local clock + process epoch — **not** cryptographic freshness and **not** replay-proof.

## Root vs approver eligibility (a bad approver cannot mint durable authority)

The reducer separates root usability from approval eligibility ([`passport-reducer.ts`](../../packages/identity/src/device-passports/passport-reducer.ts)): `requireRootRef` demands `rootActive` for a link-request create; `requireApprover` demands `rootApprovalEligible` (never true for a compromised / revoked / recovery-reverification-required root) **and**, when an approver device-authorization snapshot is supplied, that its lifecycle is exactly `active_local_unverified` — a `restricted_local` / `compromised_suspected` / `revoked_tombstone` device may **never** approve (`approver_not_operational`). The approver context is a **local root controller placeholder only** (`approverSource: "local_root_controller_placeholder"`, `cryptographicRootControlProven: false`); the module never proves cryptographic root control. Root compromise and device compromise stay separate states, but the hierarchy is enforced downward: a not-usable / not-eligible root invalidates all child passport operations, and a root recovery bumps the authority epoch so prior drafts go stale.

## Command validation (fail-closed, exact-shape)

`validateDevicePassportModelCommandV1` ([`passport-validation.ts`](../../packages/identity/src/device-passports/passport-validation.ts)) is a closed discriminated union of **10** commands — 5 link-request (`create_local` / `submit_for_review` / `reject` / `expire` / `revoke`) + 5 passport (`prepare_draft` / `approve_local_unsigned` / `restrict_local` / `expire` / `revoke`) — with **no** generic passport patch. It enforces exact schema version, exact discriminator, and exact keys (`assertExactKeys`), and rejects three purpose-built forbidden sets: **dangerous keys** (`__proto__`/`prototype`/`constructor`), **attestation/posture** (`attestation`/`devicePosture`/`screenShieldActive`/`managedBunker` → `DevicePassportAttestationConfusionError`), and a broad **authority/secret/hardware `FORBIDDEN_FIELDS`** set (`valid`/`trusted`/`verified`/`active`/`signed`/`signature`/`publicKey`/`privateKey`/`rootSecret`/`recoveryKey`/`historyKey`/`hardwareId`/`serialNumber`/`imei`/`hostname`/`osBuild`/`owner`/`admin`/`superuser`/`wildcard`/`delegationAllowed`/`remoteAccepted` → `DevicePassportValidationError`). Future-gated commands (`issue_signed`/`accept_verified`/`sign`/`verify`/`transport_qr`/`remote_accept`/`patch`) reject as `DevicePassportIssuanceUnavailableError`. Scope, capability (≤32, known values only), and key-purpose (≤16, deduplicated, known values only) shapes are validated exhaustively; every mutation carries the expected revision(s). The caller cannot set approval / signature / verification / valid / trusted / active status, key material, hardware identifiers, DevicePosture, attestation, delegation, or remote-accept flags. Raw input never appears in errors; it is explicitly **not** a hostile-input parser (Gate E).

## Policy + PolicyDecision integration (exact-scope)

`resolveDevicePassportPolicyV1` ([`passport-policy.ts`](../../packages/identity/src/device-passports/passport-policy.ts)) is pure, deterministic, fail-closed, strictest-wins across the seven privacy modes over **13** operations (5 link-request + `passport.prepare` / `approve_unsigned` / `restrict` / `expire` / `revoke` / `summary.read` + the future-gated `passport.issue_signed_future` / `passport.accept_verified_future`). Everything is `current_process_memory | null`. **Bunker** and **Emergency** deny the expansive operations (`link_request.create`/`submit`, `passport.prepare`/`approve_unsigned` via `denyExpansive`); **Emergency** permits only the restrictive set (reject / expire / revoke / restrict / summary read) via `emergencyOnly`; the future-gated pair **always** deny (`future_gated`); an unknown mode or operation denies (`unknown_input`). Strict modes suppress exact timestamps / scope details / capability details and drive summary redaction. `labelsAllowed` is **always** `false`. The structural fields are `false` in **every** mode: `cryptographicIssuanceAvailable`, `remoteAcceptanceAvailable`, `qrTransportAvailable`, `historyTransferAvailable`, `devicePostureClaimAllowed`, `attestationClaimAllowed`, `persistentStorageAllowed`, `networkAllowed`, `notificationAllowed`, `telemetryAllowed`, `aiAllowed`. The pipeline `applyDevicePassportModelCommandV1` ([`passport-pipeline.ts`](../../packages/identity/src/device-passports/passport-pipeline.ts)) maps each of the 10 commands onto an exact `PolicySideEffectScope` (`SCOPE_FOR_COMMAND`; the four link-request lifecycle commands share `identity.device_link_request.lifecycle`, and `passport.expire` shares `identity.device_passport.revoke`) and requires an authentic, allowed, **exact-scope** `PolicyDecision` — a forged, wrong-scope, or denied decision is rejected **before** mutation. In total the privacy package defines **7** passport-namespace `PolicySideEffectScope` values ([`packages/privacy/src/index.ts`](../../packages/privacy/src/index.ts): `identity.device_link_request.create`, `identity.device_link_request.lifecycle`, `identity.device_passport.prepare`, `identity.device_passport.approve_unsigned`, `identity.device_passport.restrict`, `identity.device_passport.revoke`, `identity.device_passport.summary.read`). A request/passport/device id, a root, a `RoomMemberRef`, a room role, or DevicePosture **never** authorizes.

## Pure reducer + memory/null repositories

`reduceDevicePassportModelCommandV1` ([`passport-reducer.ts`](../../packages/identity/src/device-passports/passport-reducer.ts)) is pure and deterministic: validate-before-mutate; injected ids (`DevicePassportGeneratedIdsV1`) + injected clock + process epoch + a caller-resolved root/approver context only; no storage/network/notification/AI/crypto/randomness; **no** signatures ever; **no** operational device activation; source state/command never mutated; revisions increment by one; failure yields no partial state. It also guards a process restart (`state.processEpoch !== input.processEpoch`), one draft per originating request (`draft_already_exists`), and double-approval of the originating request (`DeviceLinkRequestAlreadyApprovedError`). `InMemoryDevicePassportRepositoryV1` and `NullDevicePassportRepositoryV1` ([`passport-repository.ts`](../../packages/identity/src/device-passports/passport-repository.ts)) are memory-only / null — no disk, browser storage, database, server registry, serialized device/passport list, or export helper — with deep defensive `structuredClone`, no global singleton. Every repository operation re-checks `isAuthentic`: an authentic decision, `verdict === "allowed"`, and a `sideEffect` beginning with `identity.device_link_request.` or `identity.device_passport.` — a non-passport scope (including `storage.write` or another identity domain's `identity.device.bootstrap`) is refused (`DevicePassportDecisionMismatchError`).

## Secure Device separation

Preserved. The passport module imports only `@freelayer/privacy` (+ transitively `@freelayer/security` via identifiers), sibling identity identifiers/types, the injected-clock helpers (`../ephemeral`), and the reused TECH-ID-07 device surface (`../devices`); it imports **no** Secure Device / DevicePosture / ScreenShield / attestation implementation, no UI, no camera/QR, no transport, no crypto, no platform API, no history/message storage, and — critically — **no `@freelayer/rooms`.** The policy's honest `devicePostureClaimAllowed: false` / `attestationClaimAllowed: false` are disclosures of **absence**; a passport is an identity-owned local approval, DevicePosture is a separate RoomOS environment attribute that may only tighten, and the two never conflate. Endpoint protection (key custody, exfiltration resistance, attestation, screenshots) is the **external** Secure Device / Endpoint Defense project's concern; core keeps only contracts, policy inputs, and honest disclosures.

## Known limitations / deferred gates

Stated plainly. A Device Passport is **not** DevicePosture; a passport is **not** hardware attestation; a passport is **not** proof-of-safety; a passport is **not** proof of real-world identity. A device is **not** a person; a passport id is **not** a hardware identifier; a local unsigned approval is **not** cryptographic authorization; a QR code is only a transport representation, never authorization; room membership does **not** authorize a device; DevicePosture may **restrict** use of a device but can **neither issue nor validate** a passport. There is **no cryptographic passport** (no signature, no signed/verified passport, no verification, no fingerprints — `signatureState: "not_implemented_gate_f"`, `cryptographicallyIssued: false`), **no replay-resistant linking** (the uniqueness / one-pending / approved-once / terminal-tombstone / process-restart + deadline controls are **local structural** de-duplication, not a challenge/nonce/anti-replay proof — `cryptographicFreshnessAvailable: false`), **no remote activation/acceptance** (`operationalAuthority: "none"`, `remotelyAccepted: false`; no device becomes active), **no remote/cryptographic revocation** (a revoke is a local terminal tombstone; `LocalDevicePassportRevocationResultV1` flags all false; reconciliation is Gate H), **no hardware/posture guarantee** (`hardwareAttested: false`, `postureVerified: false`; no attestation, no posture claim), and **no endpoint guarantee** (key custody / exfiltration / transport integrity / screen-capture are external or absent; memory/null retention does not stop a compromised OS, malware, backups, or crash dumps). This is **not** a safe home for real secrets. Deferred: the signed root↔device passport signature / verification / acceptance semantics (**Gate F**), the QR / link wire format + Capsule transport (**Gate E**), the full Identity Firewall facade mapping redacted passport results and key-slot commitments to UI / Crypto (**Gate G**), and synchronization / distributed / remote passport revocation (**Gate H**). A signed, verified, attested, QR-accepted, or remotely-activated Device Passport is **not** implemented in this task — those states are named here only to negate them, and a passport is never claimed to be cryptographically valid.

## Verdict

**Complete.** The versioned, local, non-cryptographic Device Passport contract is implemented as a separate memory/null aggregate (`DevicePassportStateV1`) keyed to a caller-resolved `DevicePassportRootRefV1` + `DevicePassportApproverContextV1`, holding bounded `DeviceLinkRequestV1` candidate requests (injected-clock lifetime, ≤3 pending/root, current-process only) and attenuated unsigned `DevicePassportV1` claims (exact root/device/scope/capabilities/epoch/empty-key-slot commitments; `operationalAuthority: "none"`; `signatureState: "not_implemented_gate_f"`). It carries attenuation-only grants against both request and approver (capabilities = requested ∩ approver; add_future/recovery denied; cross-root/read-only-widen reject), an explicit terminal lifecycle whose signed issuer states are not constructible in production, authority-epoch binding that invalidates stale drafts on root recovery, fail-closed stale-context re-checks that deny on any drift and on posture/policy tightening, an approver that is a local root controller placeholder (`cryptographicRootControlProven: false`) which a restricted/compromised/revoked/ineligible root can never act as, exact-scope `identity.device_link_request.*` / `identity.device_passport.*` gating (7 scopes) enforced at the pipeline and again at the repository, a fail-closed strictest-wins policy with structural absence of signatures/issuance/verification/remote-acceptance/QR/history/attestation/persistence/network/notification/telemetry/AI, a local-only revocation with all-false remote/crypto flags, +18 Policy Matrix rows (7 structural denies/future-gates; the `device_passport_future` row reused as the Gate-F umbrella marker), a dedicated static guardrail, and honest documentation. A Device Passport is not DevicePosture, not attestation, not proof-of-safety, not real-world identity; a device is not a person; a passport id is not a hardware identifier; a local unsigned approval is not cryptographic authorization; a QR code is only a transport representation; room membership does not authorize a device. Enforcement note (see [boundary audit](DEVICE_PASSPORT_BOUNDARY_AUDIT.md)): the sdk/core Identity Firewall facade mapping redacted passport results and key-slot commitments to UI / Crypto is a later task (Gate G). Deferred: signing / verification / signature format (Gate F), QR / link wire format + Capsule transport (Gate E), full facade (Gate G), synchronization / distributed revocation (Gate H). Next: **Gate F** (cryptographic identity / signed Device Passport issuance + verification).
